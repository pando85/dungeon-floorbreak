# PLAYTRACE-01 — Record every gameplay session for deterministic replay and human-demonstration ML

**Status:** design contract, 2026-11-20, revised after two independent top-tier reviews (defaults PT-Q01..PT-Q16). **Implemented so far:** PT-A and PT-B (PR #143, the codec, the durable journal and the live adapter) and PT-C (observations per hero, the effective-input accessor, `playtrace verify` and the robustness follow-ups; see section 7.1). PT-D (the offline exporter, dataset checks and behaviour-cloning smoke, PR #161; section 7.2). PT-E is not implemented. Game feel and real-pad checks stay pending.
**Owner decision:** Every local development/playtest gameplay session with a live input source (scope and exclusions in PT-Q12), including the original demo, COMBAT-LAB-01, solo Carl, solo Donut, AI companions, two-pad co-op, retries and sandbox tests, must be recorded by default. This means authoritative game data, **not video capture**. No manual "start recording" step is acceptable in development/playtest builds.

**Priority and gate (PT-Q13):** PT-A is P1 and starts now (new files only). PT-B is P1 after #139 merges, and P0 only as the gate for COMBAT-LAB-01's first human test. **PT-B gates labelling a playtest "recorded" and COMBAT-LAB-01's first human test; it does not block the CF02-A/B owner game-feel playtest (if PT-B has merged by then, that playtest is recorded).** PT-C is P1 after AUTOPLAY-02a 02a-B merges. PT-D and PT-E are P2, deferred until at least one recorded human session exists. This recording design does not grant story-locked powers in the campaign and does not introduce ML policy execution into gameplay.

**Forward-looking parts:** section 3.4 and the "ML smoke" gate in section 5 are forward-looking and non-binding for PT-A and PT-B.

Related authority: [AUTOPLAY-01](autoplay-01-automated-gameplay-evaluation.md), [companion AI](companion-ai-command-system.md), [test strategy](testing.md), [MVP controls](../01-design/mvp-controller-contract.md), [COMBAT-LAB-01](../01-design/combat-lab-01-advanced-playtest.md), [ADR-0011](../05-decisions/ADR-0011-gameplay-session-recording.md).

## 1. Why the existing replay is insufficient

On main (2026-11-20), `src/autoplay/replay.rs` implements `autoplay-episode/1` (header + actual per-tick ActionV1 + rolling event/state hashes at 60-tick checkpoints + end), and `src/autoplay/scenario.rs` implements Carl-only fixtures. This works for verified one-actor automated tests but is **not** a universal recorder of live Bevy input, per-player-slot actions, AI-controlled Carl/Donut, context commands, physics across multiple rooms, checkpoint/retry boundaries or observation-before-action for human demonstrations. `src/party_scene.rs` already exercises `PartyState`, `SceneSim` and `CombatState` with `SlotInputs`: reuse that **one authoritative gameplay simulation**, not a parallel ML-only approximation.

Never silently repurpose `autoplay-episode/1` or overwrite its goldens. Define `playtrace-session/1` for continuous live gameplay with episode and stage segmentation; provide a version-aware bridge/exporter to existing AUTOPLAY tooling. A party format `autoplay-episode/2` and a seat-relative `ObservationV2` are **proposed in open PR #136 (AUTOPLAY-02a, AP-Q27 and AP-Q33), not merged**; do not finalize a competing game simulation API or observation schema.

**Three required products of one recording:** (1) a replayable action/event journal; (2) a human-perceived observation/action transition stream for offline learning; (3) provenance, evaluation and quality annotations. Video is optional, never a required training artifact.

## 2. Coverage and lifecycle (non-negotiable)

- **Default scope (PT-Q12).** Recording is **on by default for every `floor01_scene` run that has a live input source**: `--demo --manual`, `--cf02`, `--fixture X --manual`, story play and `floor01_scene --scene combat_lab` (LAB-00-wire). It is **off by default** for scripted and headless paths, which are already reproducible from their command line and goldens: no `--scenario`, scripted `--fixture` or `--party-fixture` without `--manual`, no `--autopilot`, `--exit-after-ticks`, `--capture-*`, `--freeze`, `--reference-frame`, `--perf-*`, `--view-trace`, headless smoke, and no presim ticks. `--record` forces recording on (rejected with presim greater than 0 unless the reset descriptor includes the presim) and `--no-record` turns it off with a visible `PLAYTRACE_` line. the v1 live binary is `floor01_scene` (including `--scene combat_lab`, added by LAB-00-wire); the greybox `src/main.rs`, `camera_lab`, `character_playground` and `companion_input_lab` are excluded in v1. "Dev/QA build" means every build from this repository while no distributable profile exists; one constant `RECORD_DEFAULT_ON` holds the default, and changing it for a distributed build needs a new ADR (see ADR-0011). Headless AUTOPLAY keeps its existing recorder. No uploads in this work, and a future distributed build needs explicit local controls and separate affirmative consent before any sharing.
- **Session start.** Start a session atomically **before the first simulated gameplay tick**. Record session ID, initial seed, build/assets and capability configuration. A session persists across scene transitions, human/AI control swaps, restarts, demo respawns, character deaths and pauses; each attempt/encounter has an independent `episode_id` and authoritative reset boundary. Preserve the failed attempt, not just the winning one.
- **Control events.** Each session has a durable, ordered sequence of **ticks** while simulation advances and **control events** (below). Paused real-world time is metadata; it does not secretly advance simulation ticks.

  | Exists on main today (v1 records these) | Future (not in v1; listed so no agent invents them) |
  | --- | --- |
  | solo swap request; pad connect, disconnect and Start join/quit; D6 disconnect pause (`d6_pause_begin/end`); `Frozen`; restart (R / Select-hold); demo respawn (Select-tap); demo checkpoint advance; exit-after; app quit | pause menu; `config_change`; level change; unlocks; companion command request/resolution (after 01A-wire / 01C) |

  Use the `RawInput` field names exactly (`move_x, jump, attack, physical, ability, pause, swap`; `RawInput` has no `down`/`interact` on main, and CF02-A adds `down`).
- **Input layers in v1 (settles the four-layer request).** v1 records `RawInput` **after the deadzone** (what the sim sees) plus pad lifecycle events. Raw stick values before the deadzone and Bevy button state are **future**. Per-slot `SlotInputs` and swap requests are recorded as provenance and as a consistency check (section 2.1), not as the replay driver. Never mistake AI for P2 or attribute AI kills to P1; log `PartyState` ownership, hero identity and source (`human_p1 | human_p2 | companion_ai | scripted_bot | none`).
- **Faithful replay.** A test replay is **faithful** only if it recreates the correct party state/ownership, geometry, hazards, enemy AI, ability resources, enemy deaths, stage resets, all ordered gameplay events and agreed authoritative state hashes. Rendering output is not expected to hash identically.
- **Observer-only rules (E3).** The recorder is passive. It must not change RNG order, hit timings, combat results, camera simulation, input edge detection, action buffer aging or AI decisions. (a) It reads `combat.events` with **its own cursor** and never calls `take_new_events()` (`src/bin/floor01_scene.rs` owns that cursor for audio and CINE). The cursor is absolute, `dropped_events + index`, because `combat.events` is capped at `EVENT_LOG_CAP = 512` and drains from the front (`dropped_events` is `pub`); it must also pick up the events of a demo respawn, which `fixed_step` emits before the step. (b) The global `t` is a recorder-owned counter; `episode_t` is `sim.world.tick`, which restart resets and demo respawn keeps. (c) New stdout lines use a `PLAYTRACE_` prefix, so existing parsers (`scripts/check_*.py`, `scripts/ci_floor01_combat.sh`) are unaffected. A test proves one logical gameplay step and one recording per tick even when Bevy render frames are skipped or duplicated.

### 2.1 Recording and replay seam (PT-Q11)

On main there is no value that holds the effective AI input before the step: `SceneSim::step_live` (`src/corridor.rs`) calls `follower_input_boss` after `step_party` has received the inputs, and the COMPANION hook `companion_inputs` (`src/combat_scene/companion.rs`) also runs inside `CombatState::step_party`. The live dispatch (swap, `hero_inputs`, `set_drive`, demo respawn/restart, stripping of attacks without combat, the D6 pause) is in the binary's `fixed_step`, and `step_combat` is binary-only. Adopted seam:

1. **Authoritative replay driver** = the per-hero routed inputs `pads.party().hero_inputs(slots)` (bit-exact `RawInput`), plus the per-tick `PartyDrive` (recorded as a `drive_change` control event only when it changes), plus the ordered lifecycle control events (`restart`, `demo_respawn`, `pad_connected/disconnected/start`, `d6_pause_begin/end`, `exit`). They are fed to `CombatState::step_party(&mut scene, inputs)`, or to `SceneSim::step_party` when combat is `None`. The verifier is a new lib module `src/playtrace/replay.rs`; it builds from a **reset descriptor** (`fixture`/`party_fixture`/`demo`/story id, `cf02_rules`, `cf02_seed`, view height, kit hash) in the `PartyFixtureSim` style and does not copy binary code.
2. **Per-slot raw inputs and swap requests** are provenance and a **consistency check**: the verifier re-derives `hero_inputs` through `PartyState` and asserts equality. They are not the replay driver.
3. **AI/bot effective inputs are re-derived during replay.** The bot and companion are deterministic code at the recorded build, and a different build is already `replay_unverified`. **PT-B makes no sim changes.** PT-C (implemented) adds one passive, **unhashed** accessor `SceneSim::last_effective_inputs() -> [RawInput; 2]`, written in `step_live`, so effective AI actions can be logged live for ML rows, with a test that every golden is unchanged with the accessor in place. Injecting recorded AI inputs into replay is explicitly **future**.
4. **Recording happens only in `fixed_step`**, after the `frozen` / `is_paused` / `exit_after` early returns and around `step_combat` / `sim.step_party`. The pre-state hash is taken before the step, the post-state hash and events after it. PT-B must **not** record the presim in `build_scene`, `perf_step`, the capture-sequence loop, `headless_*` or `view_trace` (PT-Q12).

## 3. Data contract: session, episodes, ticks and observations

All schema names are **proposed v1 defaults**, versioned independently. Use stable integer tick IDs and stable gameplay entity IDs scoped by session/episode; events carry a deterministic event ID, tick, source actor, target, cause and contact/impact attributes **only when truly observable**. Unknown attribution stays `unknown`, never guessed. Use named structured versioned enums/capabilities; avoid encoding spell names or franchise names in the generic recorder.

### 3.1 Session manifest (mandatory)

`manifest.json` stores:
- `schema`, `session_id` (locally generated, 128 bits from `std::collections::hash_map::RandomState` mixed with `SystemTime` and the process id; no new crate; non-PII), `run_kind` (`human | scripted_bot | learned_policy | mixed`), `participants` (`owner_only` default, or `includes_other_tester`, PT-Q16), `started_on_utc_day` (wall clock rounded to the day, diagnostic only, or omitted), `build_commit`, dirty/build fingerprint, binary/toolchain identity and OS family/build profile.
- **Privacy of the manifest (PT-Q16):** repo-relative paths only; no hostname, username, home path, `PadId` or vendor serial; only the glyph family or device class of an input device is kept. A tester pseudonym, if any, is typed by the tester and never derived from an account or machine name.
- `game_ruleset_id`, enabled feature flags (including `cf02_rules`), `tick_rate_hz`, content/asset/level hashes, recorded kit/scenario + variant ID, platform layout resolution, camera ruleset and RNG algorithm/seed **plus per-subsystem PRNG state when nondeterministic state cannot be reconstructed from seed alone**. Distinguish requested and effective seed.
- `action_schema_id`, `observation_schema_id` (`OBS_V2` once available, PT-Q14), `event_schema_id`, `snapshot_schema_id`, `party_schema_id`, `recorder_schema_id`, training extractor version, and exact session capability loadout/story-state/test-override flags.
- `mode` (solo Carl human, solo Donut human, local co-op), player slot mapping, input adapter versions, analog deadzone/quantization profile, assist/autoaim/accessibility settings, companion policy/profile/version/kill policy, AI internal RNG/blackboard initialization as required for replay. Never store a hardware serial, account ID or raw arbitrary device label.
- `status` (`recording | completed | abandoned | crashed_recovered | incomplete | corrupt`), `capture_complete`, `replay_verified`, `training_eligible`, `snapshot_support` (`reset_only` in v1), `quality_flags`, chunk checksums and export lineage. `manifest.json` is written as `manifest.json.tmp` and atomically renamed on finish. Mark dirty/unknown builds as `replay_unverified` until verified with the corresponding executable.
- No mutable game options may change without an ordered `config_change` event (a **future** control event, see section 2; v1 has no mutable option menu). A change that alters simulation or schema starts a new segment with a recorded state boundary; never silently mix action schemas in one episode.

### 3.2 Ordered journal

`control.jsonl` for control/lifecycle, and chunked `ticks-NNNNNN.jsonl` files (600 ticks per chunk, PT-Q15; compression deferred) for actual 60 Hz transitions. Each tick must preserve:
1. `t` monotonic recorder-owned global fixed-update tick, `episode_id`, `episode_t` (`sim.world.tick`), `stage_id`, `encounter_id`, and `pre_state_hash` (or prove reconstructed against the previous checkpoint).
2. **Pre-decision observations (PT-Q14)** for each hero/player policy. PLAYTRACE defines **no new observation type** in v1: the policy observation `o_t` is **ObservationV2 (AUTOPLAY-02a, AP-Q27) computed once per hero** (seat = carl, then seat = donut). 02a-B is asked to factor its builder to take `(&SceneSim, &CombatState, &PartyState)` instead of `&PartyFixtureSim`, so the live recorder and the AUTOPLAY env share one function (a narrow note to add to #136). The camera for visibility is the **sim `ScrollCamera`** (as AP-Q06 and AP-Q07); the live presentation-rig view rectangle is recorded per tick as a **separate diagnostic field**. A rig-based `ObservationV3` belongs to AUTOPLAY, not PLAYTRACE. `o_(t+1)` is **not stored per tick** (it is the next tick's `o_t`); it is stored only at episode terminal or truncation and at segment boundaries. Until 02a-B merges, PT-B sessions are `observation_is_partial=true` and `training_eligible=false`. Observations carry exact values and masks (`visible_enemies`, hazard visibility, ability/action availability, known resources, screen-space camera, status/telegraphs), generated by the *same visibility rules and input timing* the agent would have when acting. This is the policy input `o_t`. Multiple actors share a camera in 2P but have distinct self vectors; store both. Include an `observation_is_partial` flag if support is missing. Do **not** leak hidden HP/cooldowns, future trajectories or unseen entities into policy input.
3. Both **per-slot** `RawInput` (provenance and consistency check) and the **routed per-hero** input from `hero_inputs` (the replay driver, section 2.1), including axis values without lossy re-quantization, held buttons, `swap`, special (`ability`), and `down` (CF02-A landed: the button bit 64 of `rawinput-bits/2`; `/1` records, which have no `down`, still decode with Down released), exact press-edge semantics and explicit `available` mask. Store frame-action schema version. IEEE-754 bit-preserving encodings or a validated deterministic canonical fixed-point mapping are acceptable; generic `[-1,0,1]` compression is **not** acceptable for analog axes.
4. Human/AI control source and policy version for each hero, ordered command requests/resolutions, and a marker if a requested action was rejected/cancelled/buffered by game rules. Optional AI decision diagnostics go into a separate privileged debugging channel, **never** into learning observation tensors.
5. **Post-step** ordered deduplicated authoritative combat/world events (hit, whiff when derived, damage, death, contact, terrain destruction, hazard, hero hurt, viewer/reward event if unlocked, spell cast, mana change, spawn/despawn, actor ownership, AI order status), terminal/truncation/segment transition flags and `post_state_hash` (and `o_(t+1)` only at terminal, truncation and segment boundaries, item 2). `reward` is **not** an intrinsic human label; derive named reward profiles offline with their versions so evaluation criteria can change without recapturing games.
6. Source-of-truth actor/terrain state needed to analyze causality, from authoritative events and versioned simulation assets (periodic serializable snapshots are out of scope in v1, section 3.3). Full world-state is a **privileged diagnostic**, not policy observation; keep separate streams.

Suggested conceptual transition:
```json
{"t":120,"episode_id":"ep-2","obs_schema":"OBS_V2","obs":{"carl":"<ObservationV2, seat carl>","donut":"<ObservationV2, seat donut>"},"slots":{"p1":"<full normalized input>","p2":"<full normalized input>"},"effective":{"carl":{"source":"human_p1","action":"<exact>"},"donut":{"source":"companion_ai","policy":"companion_v0","action":"<exact>"}},"events":["<ordered event IDs and payloads>"],"post_state_hash":"<hex>"}
```
This example is a *sketch*, not a substitute for the eventual JSON Schema/typed Rust model; specify exact tensors/fields in the implementation PR and commit golden encoded samples. Use chunked files for large tick arrays (compression deferred, PT-Q15); validate complete ordering and checksums before export.

### 3.3 Snapshots, recovery and boundaries

Persist an initial **reset descriptor** (section 2.1) before tick 0, verified against a fresh reset hash. **v1 is `snapshot_support=reset_only`: adding `Serialize` to sim types (`SceneSim`, `CombatState` and their members) is out of scope for PT-A..PT-E and needs its own work order.** Nothing on `SceneSim` or `CombatState` derives `Serialize` today, so mid-run snapshots are not possible and the doc must not claim them; replay is from the reset descriptor plus the input tape and control events. If a future work order adds serialization, snapshots at every scene entry, checkpoint, retry and every 300 ticks become possible; that is future and not specified further here.

Hashes (E4): the checkpoint state hash is `CombatState::state_hash(&SceneSim)` for combat runs and `SceneSim::state_hash` for the story route; the party swap timers go into a separate `party_hash` field. The ordered-event hash is `autoplay::metrics::EventHasher` over `CombatEvent`. Cadence is `autoplay::replay::CHECKPOINT_EVERY` (60 ticks) and at every boundary. Each `ticks-NNNNNN.jsonl` chunk closes with a trailing FNV-1a-64 checksum line using `donut_mana::content_hash` / `autoplay::metrics::fnv_mix`, and is flushed when it closes. Record **logical event ordering** (pre-state, action, update, post-state) to avoid off-by-one and AI action causality errors. Use an append-only journal with per-chunk checksums, temp-file + atomic completed manifest rename, and recovery scanning. On crash, keep the valid complete prefix as `crashed_recovered`, last complete tick and a `truncated` terminal; never invent missing input/actions.

### 3.4 Training transitions and leakage prevention (forward-looking, non-binding for PT-A/B)

Exporter (PT-D, P2) produces immutable, content-addressed datasets with rows `(session_id,episode_id,t,hero_id,controlled_by,o_t,availability_mask,a_t,o_t+1,done,outcome,event_refs,labels,split)`. It is **human-imitation eligible only if the selected hero's action came from a real human** and the observation preceded that action; AI companion actions remain separate annotated samples, not impersonated demonstrations. Human-controlled Donut and AI Carl must be as supported as human-controlled Carl and AI Donut.

- **Behavioral cloning:** human `(observation, legal action)` with action timing and contiguous trajectory context; retain successful and failed attempts, idle, misses, cancel/press edges and recovery from damage. No highlight-only selection. Preserve sequential context even if an offline trainer subsamples.
- **Offline RL / reward learning:** `(obs, action, next_obs, terminal, event facts)` plus separately versioned reward functions. A player liking a kill is not inferred from score/finish/slow motion.
- **Companion imitation:** filter actual human-controlled Carl/Donut intervals and pair with legal companion observations/actions; evaluate candidate policy with the same rules and role. Do not clone erroneous P2/human kill ownership or private debug facts.
- **Diversity and difficulty:** retain scenario/seed, move timing, death cause, damage, retry sequence, enemy archetype and strategy fingerprints; aggregate by comparable ruleset. Human notes and per-room 1–5 ratings are *optional explicitly authored labels* linked to tick ranges or encounter IDs, never auto-generated ground truth.
- **Train/dev/holdout split is by full session + player pseudonym when supplied + level variant/ruleset**, not by individual ticks. No adjacent ticks or retries from the same session in both train and test; report overlap and data leakage checks. Hold-out geometry/enemy configurations must actually differ, not just have new names.
- `observation_schema` changes require an explicit transform or retraining; don't silently pad/drop fields or treat the Carl-only `ObservationV1` as full co-op perception. Record timing and latency at tick level; do not infer real human reaction times from AI input unless controls/latencies are logged.

## 4. Recorder API and integration sketch

```rust
// Design only: names/signatures may be refined without changing semantics.
trait GameplaySessionRecorder {
    fn begin_session(&mut self, manifest: SessionManifest, reset: SnapshotOrDescriptor) -> Result<(), CaptureError>;
    fn begin_episode(&mut self, boundary: EpisodeBoundary) -> Result<(), CaptureError>;
    fn record_step(&mut self, transition: PartyTransition) -> Result<(), CaptureError>;
    fn record_control(&mut self, event: SessionControlEvent) -> Result<(), CaptureError>;
    fn finish_episode(&mut self, outcome: Outcome) -> Result<(), CaptureError>;
    fn finish_session(&mut self, status: SessionStatus) -> Result<(), CaptureError>;
}
```

Place a Bevy-free recorder core in `src/playtrace/` (including `replay.rs`, section 2.1) and a **thin adapter** at the live fixed-step boundary. Share canonical event types and hashing logic with `src/autoplay/replay.rs` where appropriate; do not import Bevy into `src/autoplay/` or train in the game process. Use the existing party simulation path. **CLI location (E4):** the `list`, `inspect`, `verify` and `stats` commands are a Rust bin `src/bin/playtrace.rs`, because verification needs the sim; only the Python exporter and BC smoke (`export-transitions`, `export-bc`, PT-D) live in `tools/playtrace/**`. Add `/playtrace/` to `.gitignore` as a guard for `--record-dir` paths inside the repository.

**PT-B file ownership (E7).** PT-B may edit only `src/bin/floor01_scene.rs` (argument parsing for `--record`, `--no-record`, `--record-dir`; one resource; one pre-step and one post-step call in `fixed_step`; the REC HUD/log line), the module declaration in `src/lib.rs`, and `src/playtrace/**`. It may not edit `src/corridor.rs`, `src/combat_scene.rs`, `src/combat_scene/companion.rs` or `src/party.rs`. It lands after #139 (CF02-CORES touches only `src/acting.rs`, `src/input_buffer.rs` and `src/morale.rs`, so there is no overlap), rebases onto whichever of CF02-A/B or COMPANION 01A-wire merges first, and re-runs the golden inventory of section 5.

**Storage v1 (PT-Q15).** Directory `$XDG_DATA_HOME/dungeon-floorbreak/playtrace/<session_id>/`, falling back to `~/.local/share/dungeon-floorbreak/playtrace/`, overridable with `--record-dir`. Files: `manifest.json`, `control.jsonl` and `ticks-NNNNNN.jsonl` chunks of 600 ticks. **No compression in v1** and **no new crate** (`Cargo.toml` has only `bevy`, `serde`, `serde_json`; a compression crate needs a primary-source version check and is revisited after PT-E has measured bytes per minute; a rough estimate is about 9 MB per minute uncompressed for two float32 ObservationV2 per tick at 60 Hz, before events). A visible warning is shown when the playtrace directory exceeds **5 GB**, summed at startup; there is **no automatic deletion**. Any write error, including `io::ErrorKind::StorageFull`, marks the session `incomplete`. The writer queue is bounded at 600 ticks. The directory is outside tracked assets/source and outside git, organized by `session_id`. No network transport, no telemetry/analytics SDK, no recording of passwords, microphone audio, chat text, controller serials or free-form device identifiers. Generate an index/manifest for discovery, allow deleting sessions/exporting selected sessions, and provide a clear status indicator in dev UI/logs. **Participants (PT-Q16):** the REC indicator is shown at launch **and when P2 joins**; sessions with `participants = includes_other_tester` are excluded from export unless `--export-consented` is passed for that session. Recordings and exports are never committed to the repository.

**Failure semantics:** gameplay remains available if storage is full/unwritable, but recorder must surface a visible, actionable error, mark the affected session `incomplete` and `training_eligible=false` and never claim that all gameplay was captured. A `strict-playtest` opt-in mode may pause/reject beginning a test when capture fails; normal runtime must not freeze gameplay to satisfy a recorder. Bound asynchronous write queues, expose backpressure/dropped-tick counters and test them; **never quietly drop inputs**. Keep the PT-Q12 default (`RECORD_DEFAULT_ON`) and allow explicit `--no-record` with a visible opt-out line; tests with recording disabled must behave identically. Never silently enable collection/upload in a public distribution.

## 5. Quality gates before declaring recordings ML-ready

A session moves through **recorded → replay-verified → training-ready**. These are independent flags. Machine verification of these flags is mandatory; a complete file is not automatically a useful demonstration.

| Gate | Required result |
| --- | --- |
| Coverage | Zero missing/duplicate simulated ticks; both slots + effective per-hero inputs recorded (including neutral, simultaneous, repeated holds); scene changes, retries and interruptions intact |
| Validity | Manifest and every chunk checksum valid, monotonic tick/episode ranges, schema and asset fingerprints present, event IDs unique in scope |
| Replay | Fresh-process replay reproduces lifecycle, ownership, authoritative ordered events and state/event hashes at 60-tick checkpoints and boundaries |
| Observations | `o_t` exactly precedes action; policy observations mask invisible enemies/private timers; `o_(t+1)` is after the step; schema/availability matches actions |
| Causality | Human/AI/slot ownership and kill attribution preserved; AI companion never relabelled P2 or human |
| Recovery | Forced crash yields readable incomplete prefix; checksum corruption/missing tick rejected; recorder failure conspicuous and non-gameplay-affecting |
| Eligibility | A partial/missing observation or mismatched content/sim version excludes the segment from ML export, with exact rejection reason; raw record still retained for diagnostics |
| Isolation | With recording **on and off**, every golden stays byte-identical (inventory below), and capture on/off produces identical sim hashes and gameplay event sequences under identical seed/actions; 60-Hz tick count unaffected by render FPS. CI scripts (`scripts/ci_floor01_combat.sh`, `scripts/cf02_baseline_audit.py`) produce **no recording directory** (PT-Q12) |
| ML smoke (forward-looking, PT-D) | Small dataset from **real** live-mode human-driven actions, not synthetic test traces claimed human; exporter performs shape/edge checks; simple BC train/eval consumes it without using private diagnostics; include negative tests |
| Privacy | All output remains local; opt-out and delete work; no device serial/account data; explicit separate export/share flow |

**Golden inventory (E2).** With recording on and off, these stay byte-identical: the 20 `EXPECTED_HASHES` (13 legacy, 2 DEATH-D, 5 llama); `GOLDEN_WALK_RIGHT_400`; the story hash `931868d6afa56498`; the 7 party, 13 boss and 8 `q10_*` goldens; the `demo01_*` and CINE goldens; the autopilot hash `0363078d58558e95`; `cf02_parity_off` and `companion_stub_parity_*`; the AUTOPLAY `autoplay-episode/1` fixtures. This is the same wording as `companion-ai-01-workorder.md`.

**Required test matrix:** keyboard, DualSense/Xbox logical adapter paths where available, held and sub-frame button edges, analog stick, solo swaps in both directions, AI Carl and AI Donut, two-pad 2P, death/checkpoint/restart, pause/unpause, disconnect/reconnect, changed level, enemy knockback/hazard destruction, ability/mana, inactive/missing special, long session, full disk, unwritable directory, CI scripts producing no recording directory, crash recovery, concurrent independent recordings, same-seed replay on clean process. Unsupported current features must be listed as **pending** and not reported as passing.

**ML readiness rule:** no new multi-room human playtest may be declared a validated ML-capture session until the whole path `live input → disk → parse → fresh-process verify → export → sample inspection` passes. If full party env / serialized snapshots are not available, save complete raw recordings now and explicitly defer affected training subsets rather than fabricating support.

## 6. Workstream sequence and interfaces

- **PT-A (P1, start now) - Core contract + disk writer/reader:** `playtrace-session/1`, manifest, episode lifecycle, 600-tick chunking, exact action codec, unit tests, corruption/recovery. New files only (`src/playtrace/**`), no game logic changes and no shared-file contact.
- **PT-B (P1 after #139 merges; P0 only as the LAB-01 first-human-test gate) - Live Bevy capture adapter:** one `fixed_step` hook (section 2.1), journal-only (inputs, control events, events, hashes), default on per PT-Q12, status/errors, `src/bin/playtrace.rs` `list`/`inspect`; no sim changes, no changes to controls. Needs the concrete party input pipeline, not COMPANION-AI completion.
- **PT-C (P1 after AUTOPLAY-02a 02a-B merges) - Observation/event parity and fresh-process verifier:** ObservationV2 per hero, `SceneSim::last_effective_inputs()` accessor, `src/playtrace/replay.rs`, `verify`; synchronize with AUTOPLAY-02a and COMPANION-AI ownership. No new omniscient agent API.
- **PT-D (P2, after at least one recorded human session exists) - Offline export + smoke:** immutable datasets and leak-free split, BC extraction, metrics, schema migration tests; no production neural inference. Requires PT-C.
- **PT-E (P2, same deferral) - Playtest QA:** first owner session with capture status, replay verified and per-room human notes; measured recorder overhead on named hardware.

**Compatibility:** preserve all `autoplay-episode/1` fixtures/hashes and CF02 legacy off/on parity. If the main game or companion architecture changes mid-implementation, rebase and inspect effective fixed-tick input dispatch rather than guessing. New experiment-only unlocked abilities live behind explicit isolated capability fixtures, not the story route.

### 7.1 PT-C implementation record (adopted defaults PTI-10..PTI-20)

PTI-01..PTI-09 are recorded in PR #143. The PT-C defaults below are reversible; the owner may change any of them in a follow-up PR.

| ID | Decision | Reason |
| --- | --- | --- |
| PTI-10 | Build identity is embedded at build time by `build.rs` (std only): commit, dirty, `rustc -V`, and a **source fingerprint** (FNV-1a-64 over the toolchain line, `Cargo.toml`, `Cargo.lock` every file below `src/` and every file below `assets/data/`, which holds the sim tuning compiled in by `include_str!`; a test checks that every compile-time include lives under one of those two trees). `verify` requires the same source fingerprint (`build_mismatch` otherwise; a PT-B session has none and cannot be identified). The same source under another commit is accepted and reported `source_identical_commit_differs`. The executable fingerprint `exe-w64/1:<len>:<hash>` of the recording binary is recorded for the file, not used as the replay identity (the game and the verifier are different binaries of one source). Without git the values are `unknown` and the build never fails. | A dirty tree still has a precise identity; two binaries of one tree share it. |
| PTI-11 | `o_t` is stored per tick as `obs: [carl, donut]`, each the exact flattened `float32` bits of one ObservationV2 (`observe_v2`, the one shared builder) in `f32bits-rle-hex/1` (hex tokens, zero runs `zN`); manifest `observation_schema_id = autoplay-obs/2+f32bits-rle-hex/1`. The new tick fields are optional, so the schema stays `playtrace-session/1` and PT-B sessions still read. Measured size on this checkout (all files, uncompressed, debug build): about 0.78 KB per tick in an idle lab room and about 0.88 KB per tick in a keyboard-driven goblin-fixture session (about 3.2 MB per minute at 60 Hz). This is far below the 9 MB per minute estimate; PT-E still owns the real measurement. | One builder, exact bits, no `Serialize` on sim types. |
| PTI-12 | Privileged diagnostics are a separate stream `diagnostics.jsonl`, one line per tick, written in batches of 60: the rig view rectangle, the sim camera, exact HP, mana, hurt ticks, living and hidden enemy counts and the observation clamp counters. It is optional: a dropped line is counted (`dropped_diagnostics`) and does not make the capture incomplete. The verifier recomputes everything except the rig rectangle. | Unseen state stays out of the policy stream. No AI internals exist on main (the follower bot is scripted, `companion_ai` is reserved), so none are recorded. |
| PTI-13 | `eff` (the effective per-hero inputs of `SceneSim::last_effective_inputs`) is recorded only while the drive is live; it is `None` under the legacy drive, which has no AI hero. The accessor is written in `step_live`, never read by the sim and never hashed. | The only sim-side edit; every golden is unchanged. |
| PTI-14 | `o_(t+1)` is stored only in `episode_end.final_obs` (restart, respawn, party defeat, demo defeat, exit). For a reset inside the step (`party_defeat`, `demo_defeat_respawn`) it is the post-reset state, which is the first observation of the next episode: the defeat frame is not observable outside the step. The exit boundary stores the observation after the last tick (truncation). | A hook inside `step_party` is out of scope (no shared-file edits). |
| PTI-15 | `observation_is_partial=false` exactly when a combat state exists. The story route (`combat = None`) has no ObservationV2 builder input and stays partial (flag `no_observation_without_combat`); it still replays by hashes and effective inputs. `training_eligible` stays `false` at record time; `verify` is read-only and writes no flag. PT-D decides eligibility at export (verified, complete, human-sourced) by running the verifier. | Eligibility is a property of a verification, not of a recording. |
| PTI-16 | Verdict codes: `invalid_session`, `capture_incomplete`, `build_mismatch`, `rules_mismatch`, `content_mismatch`, `unsupported_source`, `reset_mismatch`, `control`, `episode`, `pre_state`, `slot_routing`, `labels`, `observation`, `diagnostics`, `effective_input`, `post_state`, `events`, `event_hash`, `episode_tick`, `final_observation`. Scope `full` for a finished session and `prefix` for a crash-recovered one. The per-slot inputs are checked against the routing rule applied to the recorded drive (a `PartyState` is not reconstructible from the journal); the per-tick control-source labels (`src`: which seat or hero was human, companion director, scripted bot or none, from the recorded drive, the manifest run kind and the `companion` flag) and the stage (the replayed combat checkpoint) are checked under `labels`, so relabelling AI ticks as human fails. The party swap-timer hash `ph`, the per-slot `swap` bits and the informational control events (`solo_swap`, `party_join`, `exit`, `app_quit`, episode structure) are not re-derived and the verifier says so (PT-D must treat them as unverified labels). Lab sessions are rebuilt through `LabCatalog::launch` from the manifest's lab flags. | Honest scope: a simulation replay only. |
| PTI-17 | `control.jsonl` integrity: `seq` contiguous from 0 (a gap only in an `incomplete` session with `dropped_control > 0`), `at_t` non-decreasing, and the manifest records the line count and FNV of `control.jsonl` and `diagnostics.jsonl` (`control_integrity`, `diagnostics_integrity`). A PT-B session has no record and is read with the order checks only. | A deleted line is caught even when the rest looks valid. |
| PTI-18 | A failed intermediate manifest write at chunk rotation is counted in `manifest_write_errors` (and warned once as `PLAYTRACE_WARN`); it does not make the capture incomplete because no data is lost and the final manifest is rewritten. | It is a signal, not a loss. |
| PTI-19 | Every journal line is one `write_all`; a failed or short write is truncated back to the pre-write length (`set_len`) so a retry never leaves a partial line mid-stream. | The readable prefix stays readable. |
| PTI-20 | The lab leak-guard test (`combat_lab::entry`) allows `playtrace/replay.rs`, which launches a recorded lab run through the lab's own entry-point-guarded `launch`. | The verifier must rebuild lab sessions. |

### 7.2 PT-D implementation record (adopted defaults PTD-01..PTD-20)

PT-D ships the offline exporter and the behaviour-cloning smoke as Python under `tools/playtrace/` (numpy only, nothing in the runtime Cargo build) plus two small Rust additions: `playtrace stats` and `playtrace synth-fixture`. The owner may change any value below in a follow-up PR. Usage and guarantees: [tools/playtrace/README.md](../../tools/playtrace/README.md).

| ID | Decision | Reason |
| --- | --- | --- |
| PTD-01 | The exporter never re-implements the replay: a session is exported only if the Rust `playtrace verify` exits 0 with `result=PASS scope=full`, the exporter's own structural re-check passes (chunk checksums, manifest table, contiguous ticks, control integrity) and a digest of the session files is unchanged after the verification. The verifier binary must be built from the recording's source (PTI-10 `build_mismatch` otherwise): pass it with `--verifier` or `PLAYTRACE_BIN` and the matching checkout with `--root`. Any change under `src/` or `assets/data/` changes the source fingerprint, so older sessions need the binary of their own build. | One verifier, no second replay to drift; a session cannot be edited between the check and the read. |
| PTD-02 | Rejected sessions stay in `dataset.json` under `rejected` with a stable code and detail: `invalid_journal`, `capture_incomplete`, `observation_partial`, `unsupported_schema`, `unsupported_obs_schema`, `unsupported_action_schema`, `verify_failed:<verifier code>`, `verify_not_full_scope`, `verifier_unavailable`, `modified_during_export`, `other_tester_not_consented`, `synthetic_not_allowed`, `label_mismatch`, `invalid_observation`, `illegal_action`. A structural problem inside a verified session (an illegal stick value, an observation that violates the schema) rejects the whole session; no row is dropped silently. An unknown session, observation or dataset schema is an explicit failure, never a silent pad or migration. | PT-Q08: failures retained and explained. |
| PTD-03 | One row per `(tick, hero)`. The stream is decided by the recorded control source of that hero on that tick: `human_p1`/`human_p2` go to `human/`, `companion_ai`/`scripted_bot` to `ai/`, `none` is excluded. A human hero's action is the routed per-hero input (the intent, `hero`); an AI hero's action is the effective input (`eff`). The exact bits of both are kept in the row. Rows carry a trajectory id `session-eN-hero-sK` that changes at an episode boundary, a change of control source or a gap. | Human and AI are never relabelled; swaps cut trajectories. |
| PTD-04 | Policy action `playtrace-bc-action/1`: `horizontal` (0 left, 1 neutral, 2 right at stick magnitude 0.5, the same threshold as `playtrace stats`) and the buttons `jump`, `primary` (attack), `physical`, `special` (ability), `down`. `swap` is a party command and `pause` a system button: neither is a hero action, both stay in the raw bits and are counted (`nonpolicy_bits`). A stick that is not finite or outside [-1, 1] is illegal. | ActionV1's order with the CF02 `down` appended and the reserved `swap` left out. |
| PTD-05 | Action mask `mask-rule/1`, derived from observation fields only: `special` is selectable when `available[0]` is set or the seat's own `can_cast` is set, every other component always. A pressed button the mask does not offer stays in the data and is counted as a mask violation; behaviour cloning leaves it out of the loss on that row. | The observation is the only legal source of availability. |
| PTD-06 | `next_obs` kinds: `step` (the next tick's `o_t`, same episode), `final_obs` (the `episode_end` observation after a restart, respawn or exit: `truncated`), `post_reset` (a defeat the step reset itself: `terminal`, and `next_obs` is not valid because the defeat frame is not observable, PTI-14), `missing` (the session ended without an `episode_end`: the row is a behaviour-cloning row but not a transition and is excluded from `export-transitions` as `no_next_obs`). Event facts are the absolute event ids and the rolling event hash only; the event text is build-scoped and never parsed, and no reward is exported. | Honest boundaries; PTI-02. |
| PTD-07 | Split unit: `participant_pseudonym` when a manifest supplies one, otherwise the whole session. Assignment is a deterministic ranking by a hash of `(seed, group)`; defaults dev 0.2 and holdout 0.2 with at least one training group and a dev group once there are two groups (three sessions give 2 train, 1 dev, no holdout). A leak check fails the export on any group, session, episode or trajectory in two splits and on a duplicate `(session, tick, hero)`. Scenario variants per split are reported; a within-scenario session split is **not** a hold-out of new geometry or enemies and is documented as such. Behaviour cloning refuses a dataset without a validation split. | PT-Q09. |
| PTD-08 | Datasets are content-addressed: `dataset-<id>/` with `dataset.json` (schema `playtrace-dataset/1`, sources with verify results and file digests, options, histograms, leakage report, per-file SHA-256) and per stream `rows.jsonl` plus `.npy` arrays (never `.npz`, whose zip timestamps are not deterministic). Re-exporting the same sessions and options yields the same id. The loader re-hashes every file. Output defaults outside the repository and the tool refuses an `--out` inside the checkout. | Reproducible, immutable, never committed. |
| PTD-09 | A fixture-scripted session from `playtrace synth-fixture` carries the quality flag `synthetic_fixture` and mode `synthetic_fixture`; the exporter refuses it without `--allow-synthetic`, marks the dataset and the BC report synthetic and never mixes it with real sessions. CI and committed tests use only synthetic data: a pure-Python journal with a stub verifier and sessions written by `synth-fixture` that really pass the verifier. | A synthetic trace is never passed off as a human demonstration. |
| PTD-10 | `includes_other_tester` sessions are excluded unless `--export-consented` is given together with an explicit `--session`; consent applies only to the sessions named. | PT-Q16 reads "per-session". |
| PTD-11 | The BC smoke is a numpy MLP (one 64-unit ReLU layer, a 3-way softmax for `horizontal`, sigmoid heads for the buttons, Adam, seeded and deterministic). Inputs are ObservationV2 and optionally the previous K actions of the same trajectory; nothing else is read. It reports cross-entropy, accuracy against the majority and never-pressed baselines, per-button precision, recall and F1, exact-action accuracy and (with context) the repeat-previous-action baseline, always with the caveat that it proves the pipeline and not policy quality. | Real numbers, no invented quality. |
| PTD-12 | `playtrace stats` is read-only and prints aggregate counts: sessions, ticks, episodes, combat events and per-hero human and AI action histograms. It adds no field to any record. | The aggregate view the owner can paste without raw data. |
| PTD-13 | `playtrace synth-fixture` requires an explicit `--dir` and never writes to the default recording store. | A fixture must not appear among real sessions. |
| PTD-14 | `--session` takes a **full** session id and matches the directory name exactly (one match per id; an empty id, a prefix, an unknown id or an ambiguous id is an error). `--export-consented` therefore applies only to the sessions named. | Review B-2: a prefix widened consent to other testers' sessions. This deliberately departs from the Rust CLI's unique-prefix lookup because consent is per session (PT-Q16). |
| PTD-15 | Only the control source `none` is undriven. Any other unknown source rejects the whole session with `unsupported_label`. A session whose directory name differs from its manifest `session_id` is rejected as `invalid_journal`. | Review F-1/F-6: nothing may silently vanish from the human stream, and rows are looked up by directory name. |
| PTD-16 | A session is synthetic if **any** of the quality flag `synthetic_fixture`, the mode `synthetic_fixture` or the feature flag `synthetic=true` is present; markers that disagree reject the session as `synthetic_marker_mismatch`. | Review F-4: removing one flag must not turn a fixture into a human session. |
| PTD-17 | `playtrace synth-fixture` refuses a `--dir` that resolves to the default recording store or inside it. A relative path is resolved against the working directory, existing components are canonicalized (symlinks followed), missing components are kept and `..` removes the last resolved component, so the check follows where the write would land. `playtrace stats` prints `synthetic=true|false` per session, labels synthetic hero lines `class=synthetic_human` (never `class=human`) and keeps synthetic sessions out of the `PLAYTRACE_STATS` totals, reporting them as `synthetic_sessions` and `synthetic_ticks`. | Review B-3: synthetic play must never be reported as human minutes. |
| PTD-18 | BC action context keeps the exported zero padding, and the loader adds one validity bit per context slot (from `ctx_len`) to the features. | Review F-3: `0` means "left", so padding must be distinguishable from a real previous action. |

### 7.3 The `f01_loadout` label is a roster contract (BOIL-E)

The descriptor's `f01_roster` field (PR-C, BOIL-FU; `live` or `inert`, written by every recording of the Goblin Boiler room) selects the Boiler's roster: `live` is the sidecar roster (goblins and the Engineer), `inert` the empty greybox. The verifier reads it through `f01_boiler::Roster::from_descriptor`; an unknown value fails as `content_mismatch`. A recording without the field (made before PR-C) falls back to the old rule: the `f01_loadout` label (written only by `--scene f01_late`) present means live, absent (a plain `--scene f01_boiler`) means inert. A story recording made before BOIL-E (labelled, empty room) rebuilds with enemies and fails strict verify as a state mismatch; no committed recording carries the label or the field.

The descriptor's `f01_carry` field (F01-RUN) is the story ledger a floor run (`--scene f01_late --f01-run`) carried into the recorded room: the previous room's `CombatState::story_snapshot` (a versioned `LedgerSnapshot`), passed to the room as `--f01-carry`. It is written only when set (`serde(default, skip_serializing_if)`), so it is absent in every recording made before F01-RUN, in every room launched on its own (it starts from its static pin) and in the first room of a run. The verifier rebuilds the room through its usual constructor and then applies the snapshot with `carry_story`, the binary's order (after every builder), so `start_hash` covers the carried ledger (its receipts are hashed). A carry needs a room and the story loadout (`f01_room` set, `f01_loadout` `story`), else the session fails as `rules_mismatch`; a snapshot the story table refuses (an unknown capability, a wrong hero, another version) fails as `content_mismatch`; dropping or changing the carry of a carried session changes its start state and fails verification.

## 8. Explicit non-goals

No video/voice capture requirement; no live neural companion; no personal analytics service; no training cloud; no generic save-game replacement; no inventory/progression rewrite; no new physics or per-frame indiscriminate full-world dumps; no IP-uncleared asset releases. This document provides implementation requirements, not a statement that recording works already.
