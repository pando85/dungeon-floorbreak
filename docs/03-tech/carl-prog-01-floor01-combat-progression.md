# CARL-PROG-01: Carl's Floor 01 combat progression, reconciled spec

**Status:** design adopted by recommendation under the owner's design-defaults directive (2026-11-21). Not implemented. Every value below is a data knob with a question ID (CP-Q01..CP-Q46), not approved balance. Game feel needs the owner's playtest. Delivery is split into small PRs in the [work order](../07-agents/carl-prog-01-workorder.md).

**Owner request (2026-11-21), summarized:** all existing physical moves from the start (0–20 %); enemies that demand positioning, interruptions and aerial play (20–40 %); dynamite, permanently, through a story event at about 40 % (the owner named the Hoarder; the grant is his defeat, restored in Revision 3 after Revision 2 had moved it to a find before his lair, see CP-Q01); explosive traps, launches, chain reactions and destruction taught progressively (40–80 %); after the Juicer (~85 %) the gauntlet, which gives punches stagger, armour interruption and selected material breaking; a final boss that tests mastery with no new unlock. Dynamite: Circle/B, a predictable arc, a 2.5 s fuse from release, a 64 px radius, a 7 s recharge after detonation, unlimited uses, at most one active, reduced self-damage, no friendly fire, enemy launches, structure breaking, chain reactions, no manual detonation, cooking, inventory or extra control, the existing moving-throw animation, data-driven numbers. Unlocks are narrative-event-driven, persistent and checkpoint-safe; the percentages are pacing targets only.

**Read with:** [MVP controller contract](../01-design/mvp-controller-contract.md) (authoritative for buttons), [character progression horizon](../01-design/character-progression-horizon.md), [Floor 01 progression bible](../01-design/floor-01-gameplay-progression-v0.md#carls-combat-progression-carl-prog-01), [Act I beats](../01-design/floor-01-act-01-playable-combat-beats.md), [combat-first encounters](../01-design/combat-first-encounter-design.md), [REWARDS-01](../01-design/combat-rewards-and-no-inventory-v1.md) and [ADR-0010](../05-decisions/ADR-0010-combat-first-progression.md), [COMBAT-FUN-02](../01-design/combat-fun-02-post-demo01-proposals.md), [Juicer boss](../02-art/floor-01-boss-design.md), [ANIM-CARL-03](../02-art/carl-dynamite-anim-03-spec.md), [DEATH-D](death-d-finishes-spec.md), [destruction](destruction.md), [antihero tone](../01-design/antihero-tone.md).

## 3. Unlock model: one generic story-unlock ledger

**Recommendation: one generic, IP-neutral mechanism** for every story capability. Carl's two capabilities use it now. Donut's biscuit is registered in it as a **read-through view** (`DonutMana::unlocked()` stays the storage) and migrates later in its own byte-identical PR. Reason: `src/donut_mana.rs` is pinned by hashes and is touched by DONUT-MOBILITY-01 (#173); moving its storage now risks both. `--donut-biscuit` is unchanged.

- **Module:** `src/story_unlock.rs` (new, Bevy-free). Engine types never name a franchise item or character.
  - `CapabilityId` (data ids): `special_thrown_charge` (dynamite), `fist_reinforced` (gauntlet), `primary_ranged` (biscuit, read-through). The fan layer maps display names in data. Donut's DONUT-PROG-01 (#175, `docs/03-tech/donut-prog-01-floor01-ability-progression.md` once merged) adds `jump_reach_boost` and `special_short_blink` as data rows only (CP-Q44).
  - **Capability row (CP-Q44):** `{ id, hero, slot, requires, display, cp_q }`. `hero` is the hero index the capability belongs to (data, never a name; Donut is `DONUT_HERO` 1). `slot` is `special` (the Circle/B special), `passive` or `primary_mod` (a change to the primary button). `requires` is an optional list of capability ids, default empty and unused by CARL-PROG; DONUT-PROG's story-order check fills it in and adds its validator, so it needs no schema change.
  - `UnlockLedger`: the held set per hero plus grant receipts `{ hero, capability, tick, source }`. `grant` is idempotent (a second grant returns `None` and logs nothing).
  - `StoryTrigger`: `Zone { rect }` (the `UnlockTrigger` shape) or `Event { id }`, matched against combat events through a data table (`brute_boss_f01_defeated` = `EnemyDefeated { target: BOSS_ENEMY_ID }`; the dynamite trigger `pile_boss_f01_defeated` = `EnemyDefeated { target: PILE_BOSS_ID }` names an enemy that does not exist yet, so CP-A ships the id now with a placeholder zone (CP-Q01, K1)). Once only. **A trigger carries a `grants` list**, so one story event can grant several capabilities, possibly to different heroes: it grants them in list order, on the same tick, one `CapabilityGranted` and one receipt each. The Juicer trigger `brute_boss_f01_defeated` grants `fist_reinforced` (Carl) and then Donut's `special_short_blink` (the list is authored in capability-id order, matching DP-Q03). A unit test with a two-capability, two-hero stub trigger proves the order and idempotence.
  - `StoryPin`: the declared start state of a scene (the capabilities held at tick 0). Each pin row names its scene and the story flag that owns it (`--carl-prog`, later `--donut-prog`); a scene's pin is the union of the pins of the enabled story flags. A capability's hero comes from its row, so a pin never states heroes.
- **Data:** `assets/data/gameplay/story_unlocks_v0.json` (capabilities, triggers, pins, notice text, provenance and the CP-Q ID of each row), loaded, validated and FNV-1a pinned like `companion_magic_v0.json`. A load error names the field. CP-A freezes this schema, including `hero`, `slot`, `requires` and `grants`; DONUT-PROG's DP-A adds rows and re-pins the file hash, not the schema.
- **Hash:** the ledger mixes **nothing while empty**, so every scene without a grant hashes as before. Once it holds a stored capability, it mixes a tag, the sorted `(hero, capability id)` pairs and the receipt ticks. **A read-through capability is never stored, mixed, receipted or evented by the ledger** (CP-Q45).
- **Event:** `CombatEvent::CapabilityGranted { tick, hero, capability }`, appended, emitted only on a grant of a stored capability.
- **Receipt ticks across a retry:** receipt ticks are attempt-local and keep the previous attempt's tick after a defeat retry. This is deterministic, but a retried attempt hashes differently from a fresh attempt with the same pin. It is stated here so nobody "fixes" it later.
- **PLAYTRACE data pins (CP-Q46):** `src/playtrace/live.rs` stamps data pins into `content_hashes` (`mana_tuning`, `cf02_tuning`) because `source_fingerprint` hashes only `src/`. CP-A adds `story_unlocks` and `carl_prog` pins there and the matching `check_hash` calls in `src/playtrace/replay.rs`, so a replay after a knob change fails loudly instead of diverging silently.

## 7. Final boss: mastery without unlocks

The Ball of Swine ([arena proposal](../01-design/floor-01-ball-of-swine-arena-gameplay.md)) is the mastery test. When it is designed it must:

1. Hold every Floor 01 capability from its pin and contain **no** trigger (CP-Q03, validated at load).
2. Give each Carl tool at least one authored moment where it is clearly the best answer: a kick or air kick punts a detached Tuskling into the composite; dynamite breaks a side support or stuns the ball after a wall crash; a gauntlet punch pierces a detached Tuskling's committed charge; the stomp or dive finishes a downed one.
3. Never gate damage on one tool (no dynamite-only or gauntlet-only damage window), and stay winnable in solo with an AI Donut, as the Juicer is.
4. Keep every outcome deterministic and readable without show lighting.

## 8. Gating and goldens

- **No flag, no change.** Every new rule runs only while a capability is held, and capabilities are held only through `--carl-prog` pins and triggers, `--carl-dynamite`, `--carl-gauntlet`, or a `carl_prog_*` fixture. The ledger, thrower and gauntlet mix nothing into the state hash while empty or idle; new `CombatEvent` and `MoveSpec` fields are appended.

## 10. Horizon fit and tone
